# 工程模块设计

对应源码:`src/project/` · 状态:【已确认】

## 1. 职责与边界

**职责**:工作区扫描、工程模型、章节解析、角色聚合、角色→音色绑定的持久化,以及**续传台账**。

**边界**:不合成、不调后端。可以被 `synthesis/` 读取。

## 2. 目录规范(需求指定)

```
/workspace/                         # 工作区根(卷挂载,可配置)
├── 三体/                            # 一本书 = 一个工程 = 一个隔离空间
│   ├── json/                       # 章节 JSON(输入)
│   │   ├── P01_扉页.json
│   │   └── P02_xxx.json
│   ├── process_audio/              # 中间产物
│   │   └── P01_扉页/               #   每章一个子目录
│   │       ├── 0001.wav
│   │       └── 0002.wav
│   ├── audio/                      # 章节成品
│   │   └── P01_扉页.wav
│   ├── binding.json                # 角色 → 音色 绑定
│   └── .manifest.json              # 续传台账
└── 另一本书/
```

**生命周期**:章节完全生成 → 拼接成品写入 `audio/` → **自动删除该章的 `process_audio/<章节>/`**。

## 3. 章节 JSON 解析与角色聚合

输入结构(实测 `book-json/P01_扉页.json`):

```json
[{"speaker": "旁白", "content": "扉页", "emo_vector": [0,0,0,0,0,0,0,0], "delay": 600}, ...]
```

| 字段 | 类型 | 用途 |
|---|---|---|
| `speaker` | str | 角色名 → 查绑定取音色 |
| `content` | str | 合成文本 |
| `emo_vector` | float[8] | 情感向量(顺序 喜/怒/哀/惧/厌恶/低落/惊喜/平静) |
| `delay` | int(ms) | **本条之后**的静音时长 |

**角色聚合**:扫描工程 `json/` 下所有章节,收集 `speaker` 去重 → 得到该工程的角色列表。

> 实测提醒:`P01_扉页.json` 的说话人 `旁白` 在音色库中**并不存在**(只有 `男旁白2`/`独白`/`标准女声`)。
> 这正是「角色→音色绑定」存在的意义 —— **默认不做同名自动绑定**,只做提示。

**解析容错**:

- `emo_vector` 缺失或长度 ≠ 8 → 按全零处理并告警(不中断)
- `delay` 缺失 → 默认 0;`delay` 为负 → 归零并告警
- 文本为空 → 跳过该条(不占片段编号)

## 4. 角色 → 音色 绑定

**持久化**:`<工程>/binding.json`

```json
{
  "version": 1,
  "bindings": {
    "旁白":   {"voice": "男旁白2"},
    "汪淼":   {"voice": "汪淼"},
    "常伟思": {"voice": "常伟思", "emo_ref": "叙述"}
  }
}
```

- 多个角色**可绑定同一音色**(需求指定的多对一/一对多关系)
- 未绑定的角色 → 合成时**阻塞并提示**,不静默跳过
- 音色被删除后,绑定点变为「失效」状态,UI 需高亮提醒

## 5. 续传 manifest 协议 【待评审】

> **这是整个系统最容易出错的地方,请重点过目。**

### 5.1 为什么需要它

需求原文是「扫描 `audio/` 和 `process_audio/`,只继续生成没有完成的部分」。
但**「文件存在」不等于「已完整生成」**——进程被 kill 时会留下半截文件。
若不加校验,续传会把半截音频拼进成品,产生难以察觉的**静默损坏**。

### 5.2 文件位置与结构

`<工程>/.manifest.json`:

```json
{
  "version": 1,
  "book": "三体",
  "updated_at": "2026-10-03T13:00:00Z",
  "chapters": {
    "P01_扉页": {
      "json_sha256": "a1b2c3...",
      "sentence_count": 103,
      "status": "partial",
      "output": "audio/P01_扉页.wav",
      "provider": "indextts2",
      "provider_contract_version": 1,
      "fragments": {
        "0001": {"status": "done",    "bytes": 94123, "speaker": "旁白",
                 "voice": "男旁白2", "provider": "indextts2"},
        "0002": {"status": "failed",  "attempts": 3,  "error": "HTTP 500: ..."},
        "0003": {"status": "pending"}
      }
    }
  }
}
```

### 5.3 三条硬规则

| 规则 | 内容 | 防的是什么 |
|---|---|---|
| **原子写** | 片段先写 `<name>.wav.tmp` → `os.replace()` 原子改名 | 半截文件被当成完整片段 |
| **hash 校验** | 每章记录 `json_sha256`;不匹配则**作废该章全部片段** | 换了稿子却复用旧音频(静默错配) |
| **启动对账** | 启动时用「磁盘实际状态」与 manifest 交叉校验 | manifest 与实际文件不一致 |
| **来源校验** | 每章/每片段记录 `provider` + `provider_contract_version`,不匹配则该章需重做 | 中途换 TTS 后端后,新老片段混拼导致音色/音质跳变 |

### 5.4 启动对账算法

```
对每个章节 C:
  0. 若 manifest[C].provider != 当前激活 provider
     或 manifest[C].provider_contract_version != 当前版本:
        → 该章来源不一致,作废片段并重做(保留旧成品到 audio/.stale/)
  1. 若 audio/C.wav 存在 且 manifest[C].json_sha256 == 当前 JSON hash:
        → 整章完成:清理 process_audio/C/,标记 done,跳过
  2. 若 audio/C.wav 存在 但 hash 不匹配:
        → 该章需重做(成品是旧稿的),移到 audio/.stale/ 而非直接删
  3. 若 json_sha256 不匹配(无成品):
        → 作废 process_audio/C/ 全部片段,重新生成
  4. 否则逐条对账:
        manifest 记 done 且 文件存在且字节数一致  → 跳过
        manifest 记 done 但 文件缺失/字节数不符    → 视为未完成,重生成
        manifest 无记录 但 文件存在               → 校验可解码且 > 最小字节数 → 补记 done
        manifest 记 failed/pending                → 重生成
```

> 「字节数一致」是**轻量校验**。是否额外做内容校验(如每片段的 sha256)待评审 —— 见 §7。

### 5.5 绑定变更与后端变更的处理

两条来源信息决定了「已完成的片段还算不算数」:

| 记录字段 | 变更场景 | 后果 |
|---|---|---|
| `voice`(每片段) | 用户改了某角色的音色绑定 | 该角色的片段与当前绑定不符 |
| `provider` / `provider_contract_version`(每章 + 每片段) | 用户在设置里切换了 TTS 后端 | 新老片段来自不同引擎,音色/音质会跳变 |

处理原则一致:

- 受影响的片段标记为 **stale**,UI 提示「绑定已变更,N 条片段需重新生成」
- **不自动重做**(用户可能只是试验),提供「重做受影响章节」按钮
- 整章的 `provider` 不一致时,按 §5.4 第 0 步整体重做,而非只重做部分片段 ——
  半章旧引擎、半章新引擎的成品比整体重做更糟

### 5.6 并发与落盘时机

- manifest 由**全局单例队列**持有唯一的写入者 → 无并发写问题
- **每完成一条片段就落盘一次**(整章可能几百条、耗时数十分钟,不能只靠退出时写)
- 落盘同样走原子写

### 5.7 已知风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 网络文件系统原子性 | 若 `/workspace` 是容器内的 **CIFS/NFS 挂载**,`os.replace` 的原子性可能不保证 | 推荐用 NAS 本地路径 bind mount,而非容器内再挂网络盘 |
| manifest 丢失 | 文件被误删 | 退化为「§5.4 第 4 条的兜底分支」——靠文件对账重建,最多重做少量片段 |
| 长时间运行 | 容器重启 | 架构红利:manifest 落盘 → 重启后点「全部开始」即续 |

## 6. 工作区扫描

| 场景 | 行为 |
|---|---|
| 扫描工作区 | 列出 `/workspace` 下所有含 `json/` 的目录作为工程 |
| 打开工程 | 解析章节清单 + 聚合角色 + 读绑定 + 读 manifest |
| 新建工程 | 创建 `json/ process_audio/ audio/` → 导入 JSON 文件 → 初始化 manifest |
| 非工程目录 | 不列出;UI 提供「把此目录初始化为工程」的显式操作 |

## 7. 细节决策(已定稿)

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| 1 | 片段校验强度 | **默认只比字节数**;对 `failed`/重试过的片段额外存 sha256 | 比 sha256 快得多,而「半截文件」的字节数几乎必然不符 |
| 2 | `delay` 语义 | 理解为**本条之后**的静音;**最后一条的 `delay` 也插入** | 保持全章规则一致,避免「为什么结尾少了 0.6 秒」的困惑 |
| 3 | 成品命名 | `<章节 JSON 原名>.wav`,不加序号前缀 | JSON 文件名本身有序(`P01_`/`P02_`),依赖文件名排序即可 |
| 4 | `.stale/` 旧成品 | **保留**,不自动清理 | 被作废的成品往往是唯一证据;由用户在 UI 里显式清理 |

> 补充决策 #5:**片段文件名序号宽度固定 4 位**(`0001.wav`),定义在 `models.FRAGMENT_INDEX_WIDTH`。
> 万条以上的超长章节会溢出到 5 位,字符串排序仍正确(零填充保证同宽度内有序)。

### 7.1 实现期确定的值

| 项 | 决定 | 依据 |
|---|---|---|
| 最小有效片段字节数 | **1024** | 小于此值的文件视为半截,不采纳(`MANIFEST.MIN_FRAGMENT_BYTES`) |
| `sha256` 字段存放 | 未进 `FragmentRecord`(冻结模型无此字段),由 `manifest.FragmentEntry` 子类承载 | 仅对 `failed` 或 `attempts>0` 的片段写入 |
| 章节解析告警的承载 | `chapter.py` 返回 `ChapterParseResult(chapter, warnings)` 而非裸 `Chapter` | 解析期诊断与领域实体是两个关注点;消费方取 `.chapter` |
| `.normalized` 标记内容 | JSON:`{max_seconds, max_sample_rate, at}`;`is_normalized` 只按**存在性**判定 | 符合「首次导入执行一次」,参数变化不自动重转 |
| provider 不一致 vs 绑定变更 | provider → §5.4 第 0 步**整章重做**;绑定 → §5.5 标 stale **不自动重做** | §5.5 已明确这条分野,非设计冲突 |

### 7.2 写放大实测(决定保持「每条落盘」)

§5.6 要求「每完成一条片段就落盘一次」,而实现是整文件原子重写,理论上是 O(n²)。**实测后决定保持现状**:

| 片段数 | 逐条落盘总耗时 | manifest 大小 | 折合每条 |
|---|---|---|---|
| 100 | 0.17s | 8.2KB | 1.66ms |
| 300 | 0.78s | 24.2KB | 2.60ms |
| 1000 | **3.64s** | 80.3KB | 3.64ms |

1000 条片段的合成需约 50 分钟(每条 ~3s),manifest 写盘仅占 **0.12%**。
→ 收益不抵复杂度,且「每条即时落盘」的崩溃安全性更强。

> 注:若将来真的遇到超长章节瓶颈,`save_fragment(..., persist=False)` 已经预留了批量落盘的口子。
> 批量是**安全**的 —— §5.4 第 4 条的「无记录但文件存在 → 补记 done」分支会自动收养孤儿片段。
