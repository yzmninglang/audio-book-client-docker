# 实测结论与素材现状

状态:【已确认】 — 全部结论基于 2026-10-03 的真实测量,非推断。

> 本文记录**为什么**设计长成现在这样。凡是与直觉冲突的结论,都附原始测量数据。

## 1. 素材现状

### 1.1 音色库 `reference/audio/`

- **37 个音色目录**,目录名即音色名(全中文)
- 每个目录标准结构:`1.wav`(参考音频)+ `pt.txt`(参考文本)
- 实测总量 59.0MB,平均时长 10.2s

**实测发现的三种异常结构**(设计必须处理):

| 异常 | 实例 | 含义 |
|---|---|---|
| 情感参考集 | `汪淼/` 有 6 组:`不解.wav`+`不解.txt`、`叙述`、`安慰`、`提议`、`猜测`、`略带不解和不满，解释` | 对应后端 `emo_control_method=1` + `emo_audio`,是**可用功能**,不是垃圾 |
| 人声分离产物 | `独白/1/`、`男旁白2/output_spleeter/1/` 内含 `vocals.wav` + `accompaniment.wav` | **必须排除**,否则会被误当音色 |
| 副本/异类文件 | `大佬齐静春/1 - 副本.wav`、`宁摇/*.mp3` | 需去重或忽略 |

**格式实测(重要)**:

```
32 个  WAVE PCM 16bit stereo 44100Hz
 2 个  WAVE PCM 16bit mono   16000Hz
 2 个  MP3 320kbps 44.1kHz        ← 文件名却是 1.wav
 1 个  MP3  64kbps 44.1kHz        ← 文件名却是 1.wav
```

→ **扩展名不可信**。

> 实现提示:实测 `soundfile 0.14.0` 自带 `libsndfile 1.2.2`,**支持 MP3**,且
> `sf.info()` 能直接识破伪装(`陈平安1/1.wav` 被正确报为 `MP3/MPEG_LAYER_III`)。
> 因此探测以 `soundfile` 为准,手写 magic bytes 只需作快速路径。

**⚠️ 实测发现:存在「半截」音频文件**

`标准女声/1.wav` 的 WAV 头声明 `data` 块 486400 字节,但**文件实际只有 187198 字节**。

| 读取方式 | 得到的时长 |
|---|---|
| stdlib `wave.getnframes()`(照头) | 243200 帧 → **15.2s(虚高)** |
| `soundfile`(按物理可用字节) | 93599 帧 → **5.85s(真实)** |

**影响**:

- 任何**按头部声明长度分配缓冲**的实现都会踩坑(读到越界或时长虚高)
- 参考音频的读取必须**按物理字节数夹紧帧数**
- 这从侧面印证了 [project/design.md §5](project/design.md#5-续传-manifest-协议-待评审) 的判断:
  **「文件存在」不等于「文件完整」** —— 这种半截文件在本项目里是真实存在的,不是假设

## 4. 三条判断更正(分析过程中的自我修正)

设计过程中我曾提出三个判断,实测后**被推翻**,特此记录避免后人重蹈:

| 原判断 | 实测结论 |
|---|---|
| ❌「不同音色采样率混杂会导致拼接时采样率跳变」 | 后端输出**恒为 22050Hz/16bit/mono**,与参考音频无关(内部已重采样)。此风险**不存在** |
| ❌「伪 wav(MP3)会导致后端 500」 | 实测**成功合成**。后端解码器能容错识别真实格式。转码的价值从「否则跑不通」降级为「健壮性 + 体积优化」 |
| ❌「全零 emo_vector 经后端归一化会产生音色偏移」 | `ui-api.py` **不调用** `normalize_emo_vec`(只有 `webui.py` 调),向量原样透传。零向量 ≈ 不施加情感引导,**安全** |

## 5. 关键机制发现

| 发现 | 位置 | 影响 |
|---|---|---|
| 参考音频**只取前 15 秒** | `infer_v2.py` → `_load_and_cut_audio(prompt, 15, ...)` | 超长参考音频是白传流量;入库裁剪 ≤15s 零损失 |
| 输出恒 22050 mono | 实测 | 章节拼接可**零重采样**,直接拼 PCM |
| `emo_control_method=2` 时 `emo_alpha` 默认 1.0 | `ui-api.py` | 向量不被缩放,原样生效 |
| 模型 `normalize_emo_vec` 意图上限 **0.8** | `infer_v2.py:362` | 而 API 只拒 >1.5 → **0.8~1.5 是危险区** |
| 后端无锁、无并发保护 | `ui-api.py` 全文 | 客户端**必须串行**,否则 OOM/崩溃 |
| 后端**无健康检查端点** | 路由只有一个 `/api/tts` | 「测试连接」只能用一次真实极短合成探测 |
| 服务端做 30ms 淡出 | `ui-api.py` → `audio.fade_out(30)` | 客户端拼接时**不要叠加**淡入淡出,否则段间可听见凹陷 |
| 后端有说话人缓存 | `infer_v2.py` → `cache_spk_cond` | 仅在**连续同音色**时命中;对话交替说话人时命中率低 |

## 6. 流量测算(公网传输,故必须算清)

参考音频**每个请求都要重传**。实测 37 个音色:

```
原始总量                     59.0 MB
转码后(mono, ≤22050, ≤15s)   15.9 MB     压缩比 3.7×
平均每请求(含 base64 膨胀)   ~430KB → ~573KB
```

| 规模 | 上传量 |
|---|---|
| 一章(103 条) | **~59MB** |
| 一章(300 条) | **~172MB** |
| 一本书(6000 句) | **~3.4GB** |

⚠️ **规则修正**:原方案「转码到 22050」对 16kHz 的那 2 个音色是**升采样,反而变大**。
故规则定为 **mono + 只降不升(≤22050)**。

> **未来优化(不扩边界)**:若在 `ui-api.py` 侧增加「一次上传音色、后续用 `voice_id` 引用」的端点,
> 上述 3.4GB 可降至接近 0。本次**不改后端**,但 `TTSRequest` 的参考音色字段设计为可容纳「字节」或「ID」两种形态,以后加不返工。

## 7. 安全发现

| 问题 | 说明 |
|---|---|
| 后端在**公网** | `222.20.99.34:8300` |
| **无鉴权** | `ui-api.py` 无任何凭证校验 |
| **无 TLS** | 明文 HTTP |

→ 任何知道该地址的人都能白嫖 GPU 做推理。

**本次决策**:不改后端,仅记录风险;客户端配置中**预留鉴权字段**,以后加不返工。
部署上建议客户端不直接暴露公网,走 NAS 反代/VPN,详见 [deploy/deployment.md](deploy/deployment.md)。
